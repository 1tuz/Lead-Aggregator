# Architecture

## Правило №1

`domain`, `application`, providers, `dedupe`, `storage-sqlite` и `export` не зависят от Tauri. Tauri — только desktop host.

## Слои

- `crates/domain` — модели, ошибки, `SourceKind`, provenance, теги и настройки поиска.
- `crates/provider-core` — общий контракт `DirectoryProvider` и `ProviderRuntime`: минимальная задержка, ограничение параллельности и отмена запросов.
- `crates/provider-2gis` — официальный 2GIS Places API adapter при наличии ключа, иначе public HTML adapter.
- `crates/provider-public-catalogs` — Yell, Zoon и Rusprofile public HTML adapters.
- `crates/dedupe` — нормализация телефона/домена/названия и deterministic entity resolution.
- `crates/storage-sqlite` — canonical leads + неизменяемые исходные записи источников + история `search_runs` и связь результатов с запуском.
- `crates/export` — CSV/XLSX/JSON с INN/OGRN, источниками и тегами.
- `crates/application` — параллельная оркестрация независимых источников, soft-fail одного источника, dedupe и persistence.
- `apps/desktop/src-tauri` — composition root + typed IPC.
- `apps/desktop/src` — Svelte 5 UI, без внешних HTTP-запросов.

## Дедупликация

Автоматическое объединение только по сильным ключам:

1. ИНН;
2. ОГРН;
3. нормализованный телефон;
4. домен сайта;
5. нормализованные `название + адрес`.

Одинаковое название без сильного ключа **не склеивается**: записи получают тег `Возможный дубль`. Это защищает филиалы сетей от случайного удаления.

Каждый объединенный lead сохраняет:

- `sources[]` — откуда пришли записи;
- `branches[]` — найденные адреса/координаты;
- `tags[]` — источники и статусы дедупликации;
- `dedupe.mergedRecords` — сколько исходных записей объединено.

## Source provenance

`source_records` хранит исходную нормализованную запись каждого провайдера отдельно от canonical `organizations`. Изменение алгоритма дедупликации не требует повторно обращаться к сайтам.

`organization_identities` хранит все известные сильные ключи компании (ИНН, ОГРН, телефоны, домен, название+адрес и id источников) и связывает их с постоянным canonical id. Появление более сильного ключа в следующем запуске не создаёт новую компанию.

`search_runs` хранит метаданные поиска, а `run_results` — неизменяемый JSON-снимок его результатов. История и экспорт поэтому относятся к конкретному запуску и не смешиваются с другими поисками.

## Большие сборы

Начиная с v0.4 поиск может охватывать несколько городов/регионов и десятки тысяч записей. Оркестратор разбивает такой запуск на устойчивые цели `источник × регион`.

- `collection_jobs` хранит запрос и состояние возобновляемого задания;
- `collection_job_targets` хранит контрольную точку каждой пары `источник × регион`;
- `collection_job_records` сохраняет исходные результаты завершённых целей;
- завершённые цели при возобновлении не запрашиваются повторно;
- незавершённая цель безопасно повторяется с начала, без попыток продолжать с середины HTML-страницы;
- исходные и canonical записи пишутся в SQLite пакетами;
- UI загружает результаты страницами, а экспорт читает весь снимок запуска без лимита 5000.

Каждый источник имеет собственный `ProviderSearchConfig`: лимит результатов, число страниц, задержку, параллельность и политику повторов. Пользовательские настройки не могут сделать запросы агрессивнее встроенного `ProviderPolicy`.

`429` сохраняет числовой `Retry-After`, если сервер его прислал, и прекращает текущую ветку сбора без автоматического повтора. `403`, CAPTCHA и anti-bot проверки не обходятся. Источник получает отдельный структурированный статус, не останавливая остальные источники.

Пауза источника не обрывает уже отправленный HTTP-запрос: она блокирует выдачу следующих разрешений `ProviderRuntime`. Полная отмена оставляет задание в состоянии, которое можно продолжить позже.

## Политика запросов

Каждый provider имеет собственные минимальные задержки и максимальную параллельность. Пользователь может сделать режим медленнее, но не быстрее встроенного минимума. Независимые источники запускаются параллельно, при этом `ProviderRuntime` применяет ограничения отдельно к каждому источнику.

- 2GIS: минимум 2000 ms, 1 параллельный запрос.
- Yell: минимум 2000 ms, 1.
- Zoon: минимум 3000 ms, 1.
- Rusprofile: минимум 4500 ms, 1.

По умолчанию включён только 2GIS в режиме «Бережный» (небольшие лимиты страниц). Это снижает риск CAPTCHA, но не гарантирует её отсутствие.

HTTP 403/429, CAPTCHA и anti-bot страницы не обходятся. Детектор challenge смотрит на HTTP-код, конечный URL, `<title>`, видимый текст и виджеты; слово `captcha` внутри JS/CSS само по себе не считается CAPTCHA. Проблемный provider немедленно отменяет оставшиеся собственные запросы, а остальные источники продолжают сбор независимо.

Для официального Places API ключ вводится в расширенных настройках и хранится в системном хранилище секретов через Rust backend. Он не входит в `SearchRequest`, SQLite, экспорт или generated IPC types. При сохранённом ключе 2ГИС использует HTTPS endpoints `/2.0/region/search` и `/3.0/items`, последовательно, с паузой 2000 ms; без ключа остаётся HTML provider. Для демо-ключей 2ГИС может ограничить выдачу до 10 результатов на страницу и пяти страниц. Поля контактов требуют разрешения ключа; API `429` прекращает источник и не повторяется автоматически.

## Безопасность

- Frontend CSP: только self + Tauri IPC.
- Нет Chromium/Electron/Playwright/Selenium.
- Нет чужих API-ключей и токенов.
- Нет proxy rotation, CAPTCHA solving или обхода rate limit.
- Frontend не имеет сетевых разрешений к каталогам.
